# Boldstone Review Room

Run `python3 launch.py`, or double-click **Open Boldstone Review.command**. The application opens at <http://127.0.0.1:8767>. It needs Python 3.11 or later and no new Python packages.

The app reads the published sculpture catalogue and its saved image database. It presents all active sculpture options, their retained Dropbox associations and related Squarespace/Shopify galleries. Every source keeps its qualification: a related gallery, context photograph or design reference is not silently promoted to an exact variant photograph. The image library includes unassigned and historical references as labelled records.

## Automatic folder updates

Dropbox images, file moves, folder renames and deletions are checked every minute while the local server is running. The browser checks for completed updates every ten seconds, retaining an open editor or selected images until you finish or clear the selection. **Check now** requests a scan; **Show updates** displays a completed update when editing has finished.

In v2.14.12, a component's containing-folder link also follows its retained photo IDs when the old folder has been removed and those photos now share one verified parent. This covers merging photos into an existing folder, where the original folder ID no longer exists. The recovered link is navigation only: it cannot assign every other photo in the destination to that sculpture, supply group identity defaults or authorize an automatic file move. If the photos have split across folders, the broken link is withheld and the possible folders remain recorded. Product identities, specifications and saved review choices are preserved.

## Resilient deletion reviews

Selected-file checks are saved in SQLite and run read-only with up to three workers. Closing a tab or restarting the app does not discard completed checks. Open **Jobs > Open review** to resume. Temporary read failures receive up to three attempts; a sharing or permission failure stays separate so other files can proceed. **Retry failed checks** retains successful checks. **Continue with checked files** prepares the exact checked subset for explicit confirmation; starting a review never authorizes deletion. Reviews last 24 hours, and each original's identity, revision, sharing and catalogue use are rechecked before deletion.

In v2.14.1, local database failures retry with a bounded delay and a visible worker error. A failure to write the server log cannot kill the review worker. Job/status requests revive a previously started worker if it exited; concurrent requests start only one replacement. Recovery retains completed checks and does not authorize or repeat deletion. An intentionally stopped service stays stopped.

In v2.14.2, the native file queue and image-refresh worker also recover dead threads on status/job requests. Native worker errors appear in Jobs and the navbar, and interrupted mutations remain uncertain until their results are checked. Refresh cleanup waits are bounded, failed cleanup retains the child handle, and no replacement refresh starts until that child is reaped. Stopping or disabling a service prevents revival. Failed HTTP/access logging cannot discard a saved review response; failed reads return a structured temporary error. Failed Dropbox status polls display a warning while retaining the last received catalogue, and clear that warning after a successful refresh.

In v2.14.3, preparing or retrying a deletion confirmation saves the review, batch and file memberships in one transaction. A failed local write rolls all of them back together. Overlapping read-only reviews receive independent batch memberships without repeating Dropbox checks or extending the original expiry; confirmed checks are never copied. Existing partial confirmations from earlier versions can be recovered. Reservations and a fresh explicit confirmation still prevent duplicate deletion. Automatic refreshes replace removed component pages with a clear notice and update clean specifications and listing fields; unsaved edits and navigation remain protected.

In v2.14.4, overlapping Dropbox, job-completion and transfer refreshes cannot replace a newer displayed snapshot with an older response. Failed refreshes do not prevent another successful read from being shown. Existing save, navigation and unsaved-edit guards remain in place.

In v2.14.5, navigating between sculptures closes the previous image editor after any discard decision. Image saves retain their opening sculpture and content hash, and Back/Forward or a transfer cannot interrupt an in-flight image save. Listing, Ads, shared image types and bulk choices now check the displayed content hash against the current original before saving. A filename change with unchanged bytes is accepted; replaced content requires reloading the photos. Rejected saves retain unsaved drafts, and a partial save retains the remaining unsaved form.

In v2.14.6, rapid Listing/Ads/Exclude choices for the same photo and sculpture save in click order, retaining earlier successful choices. Other photos and sculptures can still save independently. A failed earlier choice stops its queued successors without retrying an uncertain write. Original-image downloads cannot reopen closed viewers, replace newer pages or discard edits made while downloading. Move/copy forms retain their opening source and exact images, close on navigation, and reject duplicate submissions while a transfer is in flight.

In v2.14.7, Ultimate listing, Review progress and private notes save in order for each sculpture, merging only the fields changed. Queued saves retain their original sculpture, and a failed earlier choice stops its successors. Navigation waits for pending review writes and re-reads a response overtaken by a save. Exports wait for the full queued set of review choices, stop on an unconfirmed save or newly unsaved edits, and reject duplicate submission while running. Closing the tab warns while review writes are pending.

In v2.14.8, fetching a full-size original releases the catalogue lock during the download, so gallery reads and review saves can continue. Downloads are pinned to the displayed hash; the current file, duplicate group and deletion state are checked again before attaching verified metadata. Changed or removed originals require reloading, and failed downloads release their slot for a deliberate retry. Component previews and the component chooser now wait for pending review choices and re-read responses overtaken by a save; closing or switching during the wait cancels the obsolete display.

In v2.14.9, **Retry failed checks** also works from the final deletion confirmation. Retrying clears that confirmation and rebuilds the checked subset before a new confirmation; successful checks are retained and no deletion is submitted by a retry. Temporary per-file SQLite storage failures use the bounded read-retry policy instead of immediately failing the selected file. Failed checks preserve the attempt count, safe error code, HTTP status and Dropbox request ID for diagnosis; response bodies and credentials are not stored. Successful retries clear the previous error details.

A cancelled job can be reviewed again through **Jobs > Review remaining files**, with a fresh confirmation required before deletion.

In v2.14.11, newer image-type or component choices replace older unsubmitted organisation warnings in the same transaction, including failures that finish after the newer choice is saved. ## Review workflow

- **All specifications** in the left panel opens one page containing every active component and finish, grouped by family. All specification and selling fields are visible, using the same saved listing wording as exports. Search names, IDs, materials or sizes, and filter by family, listing choice, missing values, omitted fields or unreviewed fields. Listing-excluded components stay visible unless filtered out. Open **Listing copy, source details & notes** for the remaining fields and retained provenance. The overview is read-only; **Review specifications** opens the existing editor. It checks for saved updates every 15 seconds while idle, and **Refresh details** checks immediately. The URL keeps its filters. Specification and listing-editor tabs now survive reload, and **Next sculpture** retains the current tab.
- Select a sculpture and choose whether to include it in the ultimate listing. Product exclusion is separate from image exclusion.
- Review pictures individually. **Listing** and **Ads** on each card are independent toggles: both can be selected, and turning one off preserves other purposes. **Exclude** clears every purpose for that sculpture. Bulk purpose actions add the purpose to the selection without removing other uses. Open a picture for social/reference uses, primary-image selection, ordering, alt text, captions, feedback and requested edits.
- Either **Save all image changes** button in the details viewer saves image choices and shared tags. Closing the viewer warns only if its current values differ from their last saved values. Partial save failures retain the unsaved form for correction.
- Give each specification a Keep, Edit or Omit decision. Original values, estimates and source evidence stay attached. Choosing Confirmed requires an evidence note. Editing a value does not modify the canonical catalogue.
- Edit the customer-facing name, family and description in **Listing & notes**. Keep private feedback separately.
- Add shared tags and a collection/campaign name to an image. These follow the stable asset ID wherever it appears. Use the Image library to find images by name, family, tag or collection, including pictures without a sculpture association.
- The visible **Image categories** row includes **Product**, **In situ**, **Group / series** and **Detail**, with counts for the current association scope. Use the **Image types** dropdown on any card to select multiple types. Categories describe what is shown; listing/advertising/social/reference describe how to use it. A room scene can also be a group or a design reference. The type does not certify a real installation or establish a fixed set for sale.
- Cards have short buttons across multiple rows, including **Listing**, **Ads**, **In situ**, **Move** and **Review**. Use **Move** on a card or **Move / copy** on a selection to attach images to the exact destination sculpture/finish. Move removes the source title association; copy retains it. **Remove** removes only that title association. Use **Transfer history → Undo** or the **Removed from this title** view to recover. Existing purpose choices stay scoped to the original title; review uses at the destination.
- **This sculpture** initially shows selected references and files from their Dropbox folders, plus related candidates explicitly selected for listing. Broader family, other-finish and platform-gallery associations stay in **Related candidates** when excluded or kept for reference. Reviewing a wrong-finish candidate no longer pulls it into the main sculpture gallery. The category row offers **Show all associations** when additional images are outside the current scope. Neither folder membership nor type tagging certifies an exact product match.
- Category, scope and use filters are retained in shareable local routes, for example `/#BSI-A9FE7D79863A?type=in_situ` or `/#BSI-A9FE7D79863A?use=listing`. The selected primary image appears first, followed by listing images in their saved order. Per-title review reasons are visible on cards and in the image form.
- Cards and the image viewer show original bytes and known encoded pixel dimensions. A thumbnail's dimensions are never labelled as original dimensions. **Fetch Dropbox original** reads and verifies one original on demand using the already-authorized image-processing app in macOS Keychain. It requires the existing `application/.venv` runtime, downloads only inside the verified Wall Sculptures root, and rejects changed file IDs, bytes or content hashes. It cannot modify Dropbox content.
- Export a review bundle. Product decisions, specification decisions, image selections and tags are included as JSON and CSV. Listing drafts and review-ready products are separate. Optional image copies are organised under listing, advertising, social and reference folders; cached thumbnails stay in a separate preview-reference directory.
- Use **Review → Delete file…** for a Dropbox original. Choose the unwanted file and, for a duplicate, the Dropbox image to keep. Review both pictures, original dimensions/bytes, current path, file ID, revision, modification time, sharing and affected sculpture associations. Only the final **Delete this file from Dropbox** confirmation sends a deletion request. The server verifies the existing OAuth file-write scope, account/root identity, unchanged file revision/bytes and sharing before the request. The revision is also passed as Dropbox's conditional-delete guard.

Select image checkboxes to reveal **Delete…** in the selection bar. Review all selected Dropbox originals together, with a keeper for each duplicate or an unwanted-image reason. Non-Dropbox selections are listed separately and cannot be deleted. One confirmation binds the complete file-ID/revision list; selected images and their exact-byte aliases cannot be keepers. The server records batch membership and processes the reviewed files in order, preserving individual failures while continuing independent confirmed members. Results distinguish verified deletions from files not attempted. Batches and per-file receipts survive server restarts; neither a repeated request nor a status check retries deletion.

Since v2.7, deletion supports known catalogue image IDs anywhere inside **BOLDSTONE MASTER**, including the retained **Workshop and Moulding** references. A missing preview, missing pixel dimensions or missing cached size/hash does not block native inspection. The review obtains and pins available native metadata before confirmation; any already-known content hash or byte count must still match. Account/namespace identity, file-only scope, current revision, exact path and sharing checks remain in force. The automatic discovery scope remains Wall Sculptures.

If Dropbox explicitly reports the stable file ID as not found, the review instead offers to remove its leftover app entry. Confirmation rechecks absence, writes an **Already absent** receipt and suppresses that display group without sending a Dropbox deletion request. A file that reappears requires a fresh deletion review. Mixed batches distinguish real deletions from already-absent entries; failures to connect or obtain permission do not count as absence. Cached history and prior reviews are retained.

Image edit requests are a work queue, not completed pixel edits. Reviews and transfers retain the original files. The separate Delete file action removes only the explicitly reviewed Dropbox file, using normal Dropbox deletion, not permanent recovery-history purge. Recovery depends on the account's Dropbox recovery period; use **Deletion history → Open Dropbox Deleted files**. The application does not publish to Squarespace or Shopify or delete their source records. Excluding a picture from one sculpture does not exclude it from another. Shared rights marked restricted prevent public-use media copies and review-ready listing output.

**Exclude on an image card** clears every purpose for that image under the current sculpture (listing, advertising, social and reference) and clears its primary selection. It retains the original file, association, tags and review history. Choose **Ads** if the picture should be withheld from the listing but retained for advertising. Choosing another purpose reverses exclusion; previous purposes are not automatically restored. Card feedback is retained text and can describe an earlier decision; the current decision and purpose badges control the output.

## Storage and exports

Live review state is outside the project, in `~/Library/Application Support/BoldstoneReview/reviews.sqlite3`, with an append-only audit event history. Saves use per-item versions to reject conflicting edits from another tab. Every export contains a consistent SQLite backup and a `review-decisions.json` bundle with source hashes, stable IDs, original values and decisions.

Since v2.9.4, background gallery refreshes discard responses if a save started during their reads, even if that save has already finished. Transfer refreshes use the same navigation and editing guards and retry when the page is ready. A late transfer response cannot close a newer transfer dialog or clear a newer selection. Specification and notes forms keep text entered while an earlier save is pending marked as unsaved; the displayed saved value continues to show what was actually submitted.

Exports are created under `~/Library/Application Support/BoldstoneReview/exports/`. `listing-ready.csv` is a review completion projection, not a platform-specific import file or a claim of certified image resolution, physical specifications or stock. `listing-drafts.csv` includes selected products with review blockers. Available original bytes are verified against retained Dropbox content hashes. On-demand original reads additionally verify current native metadata and record their time. Other media retain their cached/preview qualification.

Specification cards show the saved listing wording, with original values and qualifications under the source disclosure. Exports and prepared projections keep certainty, evidence and source qualifications in separate fields rather than appending them to listing values. Customer-facing values use a hyphen in place of an em dash; original evidence is unchanged. The UI label Working value retains the internal `estimate` certainty code.

Review data uses these independent keys:

| Kind | Scope | Decision fields |
|---|---|---|
| `product` | stable option ID | include/exclude/pending, progress, notes |
| `field` | option ID + specification/metadata key | keep/edit/omit, value, certainty, evidence, feedback |
| `image` | option ID + stable asset ID | uses, exclude, primary, order, alt text, caption, edit request |
| `asset` | stable asset ID | multi-select types, shared tags, collection, rights, notes |
| `assignment` | option ID + preferred stable asset ID | attached/removed/source, original and target option IDs, operation ID, all identical source IDs |
| `deletion` | exact native file ID, reviewed revision and operation ID | server-owned deletion intent/receipt; executing, uncertain, deleted, already_absent or rejected |

The `__library__` image scope supports advertising/social/reference decisions independent of a product. It cannot designate a listing or primary image. Dropbox native file/folder IDs and platform gallery identities remain in the source provenance. The export does not constitute canonical or platform application; it is intended for a separate, reviewable publisher integration.

Deletion reviews and receipts are durable in the `deletion_jobs` table. Confirmed intents and results also enter the versioned reviews/event history, preserving exact file ID/revision, reviewed metadata, affected associations and keeper. Native deletions suppress the retained display group across products and exports, including historical cached aliases; the app never silently falls back to a deleted primary. This suppression does not delete other native files or historical platform aliases. Their records, original per-option reviews and cached bytes remain for audit. Deletion history reports uncertain results separately, with a read-only **Check status** action and no automatic destructive retry. The main catalogue publisher can reconcile its inventory from these receipts; existing canonical files/workbooks are not rewritten by the app.

A duplicate's chosen keeper must be a different displayed image, not another native member of the same exact-byte group. Such a keeper is rejected both before preparation and immediately before execution, so the action cannot hide an explicitly retained keeper. Manage deletion of individual native members of an already-grouped exact duplicate in Dropbox.

The local same-origin review token is retained in the mode-0600 `server-token` file so already-open tabs can save during a server upgrade. It is not a Dropbox credential.

## Exact-byte deduplication and v2 compatibility

The viewer and effective exports show one image per exact encoded-byte group, preferring Dropbox. Dropbox's block-based content hash is computed for retained platform sources and compared with retained native Dropbox content hashes; it is not compared directly with ordinary SHA256. Two matching thumbnails, similar pixels, filenames, titles and visual correspondences cannot establish original-byte equality. Resized/re-encoded versions remain separate candidates. Historical source IDs and their original associations are preserved.

Byte-identical aliases retain all original reviews. Tags/types combine; restricted rights win. Conflicting uses, exclusions or shared rights/notes are surfaced and withheld from effective public-use exports until resolved. Saving an image/shared-metadata form explicitly reconciles existing alias reviews, with versions checked atomically and old values retained in audit history. Different sculptures' choices remain independent.

`boldstone-review/v2` is additive: the original `reviews` array and consistent SQLite backup remain, alongside `effective_reviews`, `duplicate_groups`, `image-assignment-changes.csv`, `exact-byte-duplicates.csv`, and new type/original-size/source-ID columns. Existing v1 databases are retained in place; additive database tables retain reversible transfers, reviewed deletion jobs and confirmed batch membership. Removed associations are withheld from effective media output but their saved choices remain in JSON/CSV/audit records. Product/specification keys and existing statuses are unchanged. No export is automatically imported into the canonical register.

Verified originals are cached under the application data directory's `originals/`, with byte-verification receipts. Header/hash metadata is cached in `media-metadata-v1.json` and invalidated when file size, modification time or change time differs. No credentials are written to these files or exports.

The catalogue loads from `sculpture-catalogue/current-master.json` and automatically adopts a newly published, verified source before catalogue reads, review writes and queued native work. Reloading the server is no longer required after a publication. The replacement and the baseline for later Dropbox scans change together under the catalogue lock; failed verification retains the previous source and blocks dependent mutations. Existing review versions, selections, stable file IDs and job receipts are retained. Deletions still verify the current affected associations, native revision, bytes and sharing. An actual change to a reviewed file or its uses still requires renewed review. Read-only job recovery remains available during a publication failure.

**Photos & specs** on component specification cards, family component rows and image cards opens an editable contact sheet. It shows the selected primary listing image, in-situ photos, every assigned image and all current specification values. Related candidates are separate; an old source reference is not silently promoted to a selected primary. A selector switches between components without changing the gallery selection or unsaved edits.

The overview distinguishes **families with components** from **Dropbox family folders**. The folder table and sidebar expose image-only collections without inventing purchasable products. Family galleries use the recorded product folder paths to include physical folders whose names differ from the catalogue family; these folder links do not merge component identities or approve image uses.

## Automatic Dropbox images (v2.3)

While the local app server is running, it checks the authorized BOLDSTONE MASTER Wall Sculptures root every 60 seconds. The header shows the last check and offers **Check now**. Open pages check for completed image updates every 10 seconds and refresh their current gallery without navigating away. Updates wait while a form has unsaved edits, a dialog is open, an input has focus, a save is running or images are selected. No unsaved work is discarded.

The first scan follows every folder-list page; later checks use Dropbox's saved change cursor. A reset cursor triggers a complete replacement scan. A failure or incomplete listing keeps the last complete inventory. Rate-limit backoff is respected, including manual requests. New and changed originals up to 25 MB are downloaded and verified by native ID, byte count and Dropbox content hash. Larger/unsupported originals receive qualified previews; on-demand original retrieval remains available. Thumbnail dimensions are never substituted for original dimensions. Preview failures retry without blocking discovery of other uploads. Up to eight previews/originals are fetched per pass, with a local disk-space floor.

New images from a sculpture's known stable Dropbox folder appear in **This sculpture**, marked **New from Dropbox** until reviewed. Other same-family images appear as **Related candidates**; unmatched folders remain in the image library. Since v2.3.1, a current folder ending in **In Situ** (also In-Situ/In_Situ), or a descendant of that folder, supplies the **In situ** type. A sibling whose exact remaining name matches one known product folder joins that sculpture's main gallery. Ambiguous or unmatched folder stems remain candidates. Explicit types saved in the app override folder defaults, including an intentionally empty type selection. Folder-derived types update when files move or folders are renamed; their source folder IDs and links stay in the image provenance. These labels do not select listing/advertising purposes or primary images, or certify a photographed installation, manufactured finish or product identity. Tags, exclusions, transfers, specifications and other review choices remain in the existing review database. Identical byte hashes continue to display once, with Dropbox preferred. A reviewed image whose encoded bytes changed requires a fresh image-use review; old saved decisions remain in history. Files absent from a complete current inventory are withheld locally, with their historical records and reviews retained; this does not delete anything in Dropbox.

Image refresh state is separate from the published catalogue, under `~/Library/Application Support/BoldstoneReview/dropbox-sync/`. `inventory.json` atomically commits the full native index and cursor. Immutable generation snapshots bind live image data and exports to a checksum. Account/namespace/root identity is verified with the existing Keychain grant; no credentials are written to refresh state or logs. This background process has no Dropbox mutation calls and does not publish catalogue or store changes. `--no-auto-sync` is available for isolated test servers.

Since v2.3.2, image saves accept an echoed `reviewed_content_hash` from an earlier response but discard that client value before validating the editable fields. The server records the current image hash itself. Repeated Listing/Ads toggles and bulk purpose changes work in already-open tabs; unknown editable fields and stale review versions remain rejected.

## Prepared source-update integration (not enabled)

`live_review.py` prepares a verified effective source for the existing catalogue publisher to integrate. The HTTP server does not invoke it and no consumer currently treats it as authoritative. Canonical publications remain owned by the main catalogue session. Dropbox organisation now runs separately through the native jobs queue; the prepared source publisher still does not publish to online stores.

The standalone interface is `prepare(catalogue, store, output_directory)`. Use a separate QA directory until the publisher registers the intended source. `ReviewStore.snapshot()` reads reviews, transfer operations and the committed event cutoff in one SQLite transaction. Preparation checks the current published source paths and hashes before and after building the projection, rejects stale reviews, and uses one advisory writer lock per output directory.

Each generation contains immutable `data.json` and `manifest.json`; `current.json` is atomically replaced last. `status.json` records prepared, conflict or failed state. A repeated identical snapshot reuses its generation. Failed or conflicting preparation leaves the previous committed pointer in place. `read_prepared(output_directory, expected_source)` independently verifies both checksums, the event cutoff and the register/gallery hashes. A source rebase or a different review database requires a separately reviewed publication; it is not silently accepted.

The data retains original fields, qualifications, source image references, current choices, per-product exclusions, exact-byte aliases, shared types/tags, transfer provenance and withheld-image reasons. An explicitly excluded primary remains unset until the user chooses a replacement. These records do not claim that an old workbook, raw platform export or original file changed. Full snapshots currently occupy roughly 29 MB before compression; automatic publishing should use appropriate coalescing/storage management when the source is enabled. The append-only review database remains the durable operation history.

## Visual similarity and multiple sort rules

Above each image grid, **Sort by similarity** uses Apple Vision feature prints on this Mac. It arranges the current filtered images by nearest visual neighbour. Open **Sort** to add up to five rules, move rules up or down, select directions, and apply them. Available rules include folder, shared image types, purpose, file name, original pixel count, original file size, source, and listing priority. Earlier rules create groups; similarity arranges images within those groups; later rules select the starting image and break equal-distance ties. Missing original dimensions and file sizes always stay last.

Sort settings persist in this browser and are encoded in the page link. They change the gallery view, not saved listing order, image selections, shared tags, product associations, or export decisions. Reset restores the existing default order. Bulk and single-file deletion reviews now start with **Unwanted image**; the exact file review and final confirmation still apply.

Similarity requires macOS 14 or newer and the existing Swift command-line tools. The server compiles `similarity_worker.swift` on first use, then caches image features under the app runtime `similarity-v1/` directory. It uses Apple Vision revision 2 with the whole image scaled to fit. Feature generation is limited to one background worker; requests return progress without blocking gallery reads or saved edits. Only existing cached local originals/previews are read. Nothing is uploaded or downloaded by the similarity worker. Changed file content, cache file stamps, worker code, or macOS version invalidate the affected cache. New Dropbox images enter the next sort after the normal image refresh.

Damaged or incomplete ordering caches are discarded and rebuilt once during the same request. Results must retain every requested image exactly once, respect earlier sort groups and keep unavailable previews last. Invalid fresh output leaves a retryable error instead of a broken cached result. Malformed progress is ignored, old progress is cleared before a retry, and cached metadata cannot change a job's identity or status. The browser also invalidates its ordering cache when the original SHA-256 changes.

Similarity is approximate, especially across different angles, crops, lighting and backgrounds. It is not sculpture identity or exact duplication evidence. Exact-byte deduplication remains separate. Images without a usable local preview stay last in their group and are counted in the status message; the view never omits an image merely because similarity analysis is unavailable.
