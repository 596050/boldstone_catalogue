# Boldstone Review Room

Run `python3 launch.py`, or double-click **Open Boldstone Review.command**. The application opens at <http://127.0.0.1:8767>. It needs Python 3.11 or later and no new Python packages.

The app reads the published sculpture catalogue and its saved image database. It presents all 188 active sculpture options, their retained Dropbox associations and related Squarespace/Shopify galleries. Every source keeps its qualification: a related gallery, context photograph or design reference is not silently promoted to an exact variant photograph. The image library includes unassigned and historical references as labelled records.

## Review workflow

- Select a sculpture and choose whether to include it in the ultimate listing. Product exclusion is separate from image exclusion.
- Review pictures individually. **Listing** and **Ads** on each card are independent toggles: both can be selected, and turning one off preserves other purposes. **Exclude** clears every purpose for that sculpture. Bulk purpose actions add the purpose to the selection without removing other uses. Open a picture for social/reference uses, primary-image selection, ordering, alt text, captions, feedback and requested edits.
- Either **Save all image changes** button in the details viewer saves image choices and shared tags. Closing the viewer warns only if its current values differ from their last saved values. Partial save failures retain the unsaved form for correction.
- Give each specification a Keep, Edit or Omit decision. Original values, estimates and source evidence stay attached. Choosing Confirmed requires an evidence note. Editing a value does not modify the canonical catalogue.
- Edit the customer-facing name, family and description in **Listing & notes**. Keep private feedback separately.
- Add shared tags and a collection/campaign name to an image. These follow the stable asset ID wherever it appears. Use the Image library to find images by name, family, tag or collection, including pictures without a sculpture association.
- The visible **Image categories** row includes **Product**, **In situ**, **Group / series** and **Detail**, with counts for the current association scope. Choose **Types** on any card to jump directly to the multi-select image-type controls. Categories describe what is shown; listing/advertising/social/reference describe how to use it. A room scene can also be a group or a design reference. The type does not certify a real installation or establish a fixed set for sale.
- Cards have two rows of short buttons: **Listing / Ads / Exclude**, then **Move / Types / Review**. Use **Move** on a card or **Move / copy** on a selection to attach images to the exact destination sculpture/finish. Move removes the source title association; copy retains it. **Remove** removes only that title association. Use **Transfer history → Undo** or the **Removed from this title** view to recover. Existing purpose choices stay scoped to the original title; review uses at the destination.
- **This sculpture** initially shows selected references and files from their Dropbox folders, plus related candidates explicitly selected for listing. Broader family, other-finish and platform-gallery associations stay in **Related candidates** when excluded or kept for reference. Reviewing a wrong-finish candidate no longer pulls it into the main sculpture gallery. The category row offers **Show all associations** when additional images are outside the current scope. Neither folder membership nor type tagging certifies an exact product match.
- Category, scope and use filters are retained in shareable local routes, for example `/#BSI-A9FE7D79863A?type=in_situ` or `/#BSI-A9FE7D79863A?use=listing`. The selected primary image appears first, followed by listing images in their saved order. Per-title review reasons are visible on cards and in the image form.
- Cards and the image viewer show original bytes and known encoded pixel dimensions. A thumbnail's dimensions are never labelled as original dimensions. **Fetch Dropbox original** reads and verifies one original on demand using the already-authorized image-processing app in macOS Keychain. It requires the existing `application/.venv` runtime, downloads only inside the verified Wall Sculptures root, and rejects changed file IDs, bytes or content hashes. It cannot modify Dropbox content.
- Export a review bundle. Product decisions, specification decisions, image selections and tags are included as JSON and CSV. Listing drafts and review-ready products are separate. Optional image copies are organised under listing, advertising, social and reference folders; cached thumbnails stay in a separate preview-reference directory.
- Use **Review → Delete file…** for a Dropbox original. Choose the unwanted file and, for a duplicate, the Dropbox image to keep. Review both pictures, original dimensions/bytes, current path, file ID, revision, modification time, sharing and affected sculpture associations. Only the final **Delete this file from Dropbox** confirmation sends a deletion request. The server verifies the existing OAuth file-write scope, account/root identity, unchanged file revision/bytes and sharing before the request. The revision is also passed as Dropbox's conditional-delete guard.

Select image checkboxes to reveal **Delete…** in the selection bar. Review all selected Dropbox originals together, with a keeper for each duplicate or an unwanted-image reason. Non-Dropbox selections are listed separately and cannot be deleted. One confirmation binds the complete file-ID/revision list; selected images and their exact-byte aliases cannot be keepers. The server records batch membership and processes the reviewed files in order, stopping on the first rejection or unconfirmed result. Results distinguish verified deletions from files not attempted. Batches and per-file receipts survive server restarts; neither a repeated request nor a status check retries deletion.

Image edit requests are a work queue, not completed pixel edits. Reviews and transfers retain the original files. The separate Delete file action removes only the explicitly reviewed Dropbox file, using normal Dropbox deletion, not permanent recovery-history purge. Recovery depends on the account's Dropbox recovery period; use **Deletion history → Open Dropbox Deleted files**. The application does not publish to Squarespace or Shopify or delete their source records. Excluding a picture from one sculpture does not exclude it from another. Shared rights marked restricted prevent public-use media copies and review-ready listing output.

**Exclude on an image card** clears every purpose for that image under the current sculpture (listing, advertising, social and reference) and clears its primary selection. It retains the original file, association, tags and review history. Choose **Ads** if the picture should be withheld from the listing but retained for advertising. Choosing another purpose reverses exclusion; previous purposes are not automatically restored. Card feedback is retained text and can describe an earlier decision; the current decision and purpose badges control the output.

## Family overviews and image coverage

Click a family heading in the left selector to open its overview. It shows individual options, existing component identities, unique retained images, options below the two-in-situ-image target, and plain White entry/title/individual-photo checks. Family links can be bookmarked (`#family=Acanthus`). Product checklists and sidebar indicators update after review choices, tags, transfers and deletions.

Use the arrow beside a family heading to collapse or expand its sculpture list. **Collapse all** and **Expand all** act across the families. Choices are remembered in this browser and survive page reloads and image refreshes. Search and sidebar filters temporarily reveal matching families; clearing the filters restores the remembered layout. Family names still open their overviews. Collapsing a family does not change the open sculpture or any review choices.

The in-situ target is two distinct, non-excluded Dropbox images per individual option. Counts use current saved native metadata and deletion receipts, the sculpture association and your image-type tags; related candidates and platform-only images do not count until the relevant Dropbox image is assigned or selected for that sculpture. Exact-byte groups count once. In-situ tags can include group scenes and mock-ups, so coverage is not proof of a real photographed installation. The separate listing count shows how many in-situ images are selected for listing. Excluded products are outside the target.

Plain White checks follow existing component IDs and published working design groups, including owner-confirmed Decowaves equivalences. Counts distinguish retained component records from working design groups. Product/finish identities and photographs remain separate; an equivalent design does not transfer image approval, specifications or stock. A named White option counts as an entry; a generic title whose containing folder ends in White is flagged as a title check. Mixed-colour and marbled variants do not satisfy plain White. Missing entry, excluded entry, omitted White title and missing individual product image are separate states. Components not defined in the catalogue remain unevaluated. These indicators do not create or rename products, certify finishes or add photographs.

Each product now explains its complete retained-image count, its This sculpture count, related candidates by source, and any removed associations, with shortcuts to the corresponding views. Category counts and visible cards continue to follow the current filters. For Acanthus Flower, the initial eight retained associations were four assigned Dropbox images and four related Squarespace gallery images. Nonidentical platform versions remain provenance candidates; they are not silently treated as approved product photographs.

## Storage and exports

Live review state is outside the project, in `~/Library/Application Support/BoldstoneReview/reviews.sqlite3`, with an append-only audit event history. Saves use per-item versions to reject conflicting edits from another tab. Every export contains a consistent SQLite backup and a `review-decisions.json` bundle with source hashes, stable IDs, original values and decisions.

Exports are created under `~/Library/Application Support/BoldstoneReview/exports/`. `listing-ready.csv` is a review completion projection, not a platform-specific import file or a claim of certified image resolution, physical specifications or stock. `listing-drafts.csv` includes selected products with review blockers. Available original bytes are verified against retained Dropbox content hashes. On-demand original reads additionally verify current native metadata and record their time. Other media retain their cached/preview qualification.

Specification cards show the saved listing wording, with original values and qualifications under the source disclosure. Exports and prepared projections keep certainty, evidence and source qualifications in separate fields rather than appending them to listing values. Customer-facing values use a hyphen in place of an em dash; original evidence is unchanged. The UI label Working value retains the internal `estimate` certainty code.

Review data uses these independent keys:

| Kind | Scope | Decision fields |
|---|---|---|
| `product` | stable option ID | include/exclude/pending, progress, notes |
| `field` | option ID + specification/metadata key | keep/edit/omit, value, certainty, evidence, feedback |
| `image` | option ID + stable asset ID | uses, exclude, primary, order, alt text, caption, edit request |
| `asset` | stable asset ID | multi-select types, shared tags, collection, rights, notes |
| `assignment` | option ID + preferred stable asset ID | attached/removed/source, original and target option IDs, operation ID, all identical source IDs |
| `deletion` | exact native file ID, reviewed revision and operation ID | server-owned deletion intent/receipt; executing, uncertain, deleted or rejected |

The `__library__` image scope supports advertising/social/reference decisions independent of a product. It cannot designate a listing or primary image. Dropbox native file/folder IDs and platform gallery identities remain in the source provenance. The export does not constitute canonical or platform application; it is intended for a separate, reviewable publisher integration.

Deletion reviews and receipts are durable in the `deletion_jobs` table. Confirmed intents and results also enter the versioned reviews/event history, preserving exact file ID/revision, reviewed metadata, affected associations and keeper. Native deletions suppress the retained display group across products and exports, including historical cached aliases; the app never silently falls back to a deleted primary. This suppression does not delete other native files or historical platform aliases. Their records, original per-option reviews and cached bytes remain for audit. Deletion history reports uncertain results separately, with a read-only **Check status** action and no automatic destructive retry. The main catalogue publisher can reconcile its inventory from these receipts; existing canonical files/workbooks are not rewritten by the app.

A duplicate's chosen keeper must be a different displayed image, not another native member of the same exact-byte group. Such a keeper is rejected both before preparation and immediately before execution, so the action cannot hide an explicitly retained keeper. Manage deletion of individual native members of an already-grouped exact duplicate in Dropbox.

The local same-origin review token is retained in the mode-0600 `server-token` file so already-open tabs can save during a server upgrade. It is not a Dropbox credential.

## Exact-byte deduplication and v2 compatibility

The viewer and effective exports show one image per exact encoded-byte group, preferring Dropbox. Dropbox's block-based content hash is computed for retained platform sources and compared with retained native Dropbox content hashes; it is not compared directly with ordinary SHA256. Two matching thumbnails, similar pixels, filenames, titles and visual correspondences cannot establish original-byte equality. Resized/re-encoded versions remain separate candidates. Historical source IDs and their original associations are preserved.

Byte-identical aliases retain all original reviews. Tags/types combine; restricted rights win. Conflicting uses, exclusions or shared rights/notes are surfaced and withheld from effective public-use exports until resolved. Saving an image/shared-metadata form explicitly reconciles existing alias reviews, with versions checked atomically and old values retained in audit history. Different sculptures' choices remain independent.

`boldstone-review/v2` is additive: the original `reviews` array and consistent SQLite backup remain, alongside `effective_reviews`, `duplicate_groups`, `image-assignment-changes.csv`, `exact-byte-duplicates.csv`, and new type/original-size/source-ID columns. Existing v1 databases are retained in place; additive database tables retain reversible transfers, reviewed deletion jobs and confirmed batch membership. Removed associations are withheld from effective media output but their saved choices remain in JSON/CSV/audit records. Product/specification keys and existing statuses are unchanged. No export is automatically imported into the canonical register.

Verified originals are cached under the application data directory's `originals/`, with byte-verification receipts. Header/hash metadata is cached in `media-metadata-v1.json` and invalidated when file size, modification time or change time differs. No credentials are written to these files or exports.

The catalogue loads from `sculpture-catalogue/current-master.json` at server startup. To refresh specifications or identities after a new canonical publication, stop this server using its saved PID and reopen the launcher. Existing reviews remain versioned; source-hash changes stay visible in exports and are flagged for re-review. Do not overwrite the review database when refreshing sources.

## Automatic Dropbox images (v2.3)

While the local app server is running, it checks the authorized BOLDSTONE MASTER Wall Sculptures root every 60 seconds. The header shows the last check and offers **Check now**. Open pages check for completed image updates every 10 seconds and refresh their current gallery without navigating away. Updates wait while a form has unsaved edits, a dialog is open, an input has focus, a save is running or images are selected. No unsaved work is discarded.

The first scan follows every folder-list page; later checks use Dropbox's saved change cursor. A reset cursor triggers a complete replacement scan. A failure or incomplete listing keeps the last complete inventory. Rate-limit backoff is respected, including manual requests. New and changed originals up to 25 MB are downloaded and verified by native ID, byte count and Dropbox content hash. Larger/unsupported originals receive qualified previews; on-demand original retrieval remains available. Thumbnail dimensions are never substituted for original dimensions. Preview failures retry without blocking discovery of other uploads. Up to eight previews/originals are fetched per pass, with a local disk-space floor.

New images from a sculpture's known stable Dropbox folder appear in **This sculpture**, marked **New from Dropbox** until reviewed. Other same-family images appear as **Related candidates**; unmatched folders remain in the image library. Since v2.3.1, a current folder ending in **In Situ** (also In-Situ/In_Situ), or a descendant of that folder, supplies the **In situ** type. A sibling whose exact remaining name matches one known product folder joins that sculpture's main gallery. Ambiguous or unmatched folder stems remain candidates. Explicit types saved in the app override folder defaults, including an intentionally empty type selection. Folder-derived types update when files move or folders are renamed; their source folder IDs and links stay in the image provenance. These labels do not select listing/advertising purposes or primary images, or certify a photographed installation, manufactured finish or product identity. Tags, exclusions, transfers, specifications and other review choices remain in the existing review database. Identical byte hashes continue to display once, with Dropbox preferred. A reviewed image whose encoded bytes changed requires a fresh image-use review; old saved decisions remain in history. Files absent from a complete current inventory are withheld locally, with their historical records and reviews retained; this does not delete anything in Dropbox.

Image refresh state is separate from the published catalogue, under `~/Library/Application Support/BoldstoneReview/dropbox-sync/`. `inventory.json` atomically commits the full native index and cursor. Immutable generation snapshots bind live image data and exports to a checksum. Account/namespace/root identity is verified with the existing Keychain grant; no credentials are written to refresh state or logs. This background process has no Dropbox mutation calls and does not publish catalogue or store changes. `--no-auto-sync` is available for isolated test servers.

Since v2.3.2, image saves accept an echoed `reviewed_content_hash` from an earlier response but discard that client value before validating the editable fields. The server records the current image hash itself. Repeated Listing/Ads toggles and bulk purpose changes work in already-open tabs; unknown editable fields and stale review versions remain rejected.

## Prepared source-update integration (not enabled)

`live_review.py` prepares a verified effective source for the existing catalogue publisher to integrate. The HTTP server does not invoke it and no consumer currently treats it as authoritative. The requested target (consolidated catalogue, Dropbox organisation or online stores) remains to be clarified. Existing canonical publications remain owned by the main catalogue session.

The standalone interface is `prepare(catalogue, store, output_directory)`. Use a separate QA directory until the publisher registers the intended source. `ReviewStore.snapshot()` reads reviews, transfer operations and the committed event cutoff in one SQLite transaction. Preparation checks the current published source paths and hashes before and after building the projection, rejects stale reviews, and uses one advisory writer lock per output directory.

Each generation contains immutable `data.json` and `manifest.json`; `current.json` is atomically replaced last. `status.json` records prepared, conflict or failed state. A repeated identical snapshot reuses its generation. Failed or conflicting preparation leaves the previous committed pointer in place. `read_prepared(output_directory, expected_source)` independently verifies both checksums, the event cutoff and the register/gallery hashes. A source rebase or a different review database requires a separately reviewed publication; it is not silently accepted.

The data retains original fields, qualifications, source image references, current choices, per-product exclusions, exact-byte aliases, shared types/tags, transfer provenance and withheld-image reasons. An explicitly excluded primary remains unset until the user chooses a replacement. These records do not claim that an old workbook, raw platform export or original file changed. Full snapshots currently occupy roughly 29 MB before compression; automatic publishing should use appropriate coalescing/storage management when the source is enabled. The append-only review database remains the durable operation history.

## Development and checks

```sh
python3 -m unittest discover -s tests -v
python3 server.py --port 8768 --data-dir '/tmp/boldstone-review-test'
```

Only `127.0.0.1` is bound. Writes require a same-origin review-session token. Cached files are served only through known catalogue asset IDs; arbitrary filesystem paths are not accepted. Test reviews must use a separate data directory.
